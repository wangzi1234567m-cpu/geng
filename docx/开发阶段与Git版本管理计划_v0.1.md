# 双人梗簿开发阶段与 Git 版本管理计划

2026年11月6日｜v0.1｜执行计划建议稿

依据当前需求决策记录、分层主体架构及 API 数据库契约草案制定。阶段名称、流程和质量门槛为本次建议，尚未表示开发已完成或已有验收结果。未确定人员、预算和试用规模，因此不编造工期或上线日期。

## 1 当前状态与计划范围

已完成需求和分层设计讨论，具备技术选型建议、OpenAPI 草案和数据库逻辑模型。目前目录不是 Git 仓库；没有实施后端、Android、实际数据库迁移、云部署或接口联调。现有 Word PRD 尚未与需求决策补充完全同步，阶段 0 先解决这一基线问题。

本计划覆盖首版邮箱密码登录、验证邮箱、双人空间、邮箱或用户 ID 邀请、梗文字与背景及图片、共同编辑、退出冻结、永久删除、注销清除、大陆 Docker 部署和小范围试用。语音与多人空间不进入首版，只检查现有结构是否允许后续合理扩展。

推荐以纵向功能逐步交付：每阶段包含所需领域逻辑、应用用例、接口、Android 入口与验证，不采取先写完全部后端再一次性做客户端的方式。基础授权、状态检查及事务入口从第一条业务写入起生效，不能等生命周期阶段才补。

## 2 Git 仓库与工作方式

### 2.1 单仓库

推荐一个私有仓库统一管理客户端、后端、契约、迁移和部署，便于同一个变更同时修改相关契约与实现。远程平台尚未决定，可优先评估 GitHub 私有仓库及其 CI；应核对实际套餐支持的分支保护和审批功能，不声称已经启用。

建议未来目录如下，属于整理目标，不表示本次已移动现有文件：

```text
android/                  Android 客户端
backend/                  分层服务端与后台任务
contracts/                OpenAPI 与数据库模型
deploy/                   Docker、部署模板及运维脚本
docs/                     当前需求、架构、决策和验收说明
tools/                    可复用生成与检查工具
docx/                     Word 文档与当前已有设计稿
```

代码、构建锁定文件、数据库迁移、契约及源文档纳入 Git。Markdown 作为可审查的文档源，Word 作为同步导出的阅读版本；阶段 0 明确唯一有效基线与变更记录，避免多个版本互相矛盾。

### 2.2 分支与提交

`main` 保存已通过当前适用检查、可重复构建的集成代码；在首版功能未完成时不将其误称为已可公开上线。每项工作创建短期分支，如 `feat/email-auth`、`feat/space-invitations`、`fix/frozen-space-write`、`docs/api-contract`。

每个分支对应一个可审查任务。推荐通过 PR 合并，使用 squash 保留清晰主线，不额外维护长期 develop 分支。main 不直接开发、不强制推送、不重写已发布历史。个人分支重写前也要确认无人依赖；本计划不自动授权任何破坏性 Git 操作。

提交消息采用简单类型与范围，例如：

```text
feat(auth): 支持邮箱验证后登录
feat(entries): 保存梗时校验记录版本
fix(media): 拒绝冻结后的图片关联
docs(contracts): 明确注销回执行为
```

提交说明应解释行为与必要原因，不把密码、邮箱、令牌或真实回忆写进提交消息、分支名、Issue、PR 或截图。

### 2.3 合并门槛

- 分支同步并通过适用的构建、格式和检查；不存在未处理的合并冲突。
- 关联任务包含目标、边界和验收条目，PR 说明实际改动及验证证据。
- 涉及 API、迁移或权限规则时，同步更新相应契约与说明。
- 多人开发时由另一位开发者审查；单人阶段用 CI 和自查记录，不虚构独立评审已发生。
- 未完成的高风险能力不向试用用户暴露。不能用“后面会修”绕过权限、数据丢失或错误删除问题。

分支保护与必需检查应在平台支持时配置，并验证确实生效；这是待执行动作，不是已具备的状态。[S1]

### 2.4 仓库隐私与秘密

Git 不保存真实 .env、云密钥、数据库密码、Android 签名私钥、用户图片、数据库备份、生产日志和真实试用资料。配置模板只含假值；构建产物、缓存和本地数据通过精确的忽略规则排除。可复用工具脚本仍需纳入版本，不因位于临时工作目录就一概丢弃。

加入 .gitignore 不会清除已经被跟踪的内容或历史中的秘密。发现泄露先撤销和轮换凭据，再按影响决定清理历史；仅删除当前文件不能视为已解决。[S2] 私有仓库也不替代秘密扫描和最小访问权限。

Git 保护的是代码和设计历史，不是用户回忆的备份或版本功能。用户永久删除不能通过仓库历史被恢复，因为真实内容不应进入 Git。

## 3 阶段 0 需求与契约基线

目标：让开发、客户端及验收使用同一套规则。

交付：同步后的 PRD、当前架构说明、经评审的技术选型、核心页面原型、OpenAPI 与数据库设计基线、剩余决策清单。技术栈目前仍是推荐，进入编码前需确定采用方案。

验收标准：

- Word PRD 与最新决策一致，明确共同编辑删除、退出冻结、注销优先清除和注销同时冻结。
- 记录必填性、待加入空间能否发布、注销后的占位身份等影响首批实现的分支已经决定。
- 图片和正文容量、邀请及票据期限等可以配置，但必须在对应功能最终验收前给出确定值；删除与备份时限最迟在真实试用前确定。
- 核心原型覆盖注册验证、邀请、发布与编辑、删除、退出和注销；失败与冲突不只有成功页面。
- OpenAPI 通过规范检查、引用检查与客户端模型生成验证；DBML 不被误当成已经可以部署的迁移。
- 待确认项有影响阶段和解决时点，不以编造默认需求完成验收。

证据：需求决策清单、原型、契约检查结果和基线提交。阶段通过不表示程序已可运行。

## 4 阶段 1 Git 与工程基础

目标：从干净检出可重复构建，为后续功能设置统一安全入口。

交付：本地 Git 仓库、确定后的远程私有仓库配置、目录结构、Android 与后端骨架、数据库迁移框架、开发 Compose、配置模板及基础 CI。

验收标准：

- 新环境按 README 可以检出、构建 Android 调试包、启动后端与开发数据库，不依赖某台机器的私有绝对路径。
- 数据库空实例可以迁移到当前版本；已应用迁移不随意修改，后续变更新增迁移。
- API 认证入口、统一错误格式、私密日志脱敏、事务协调与领域状态检查的基础结构已存在；无权限默认拒绝。
- 业务代码没有循环依赖，API 不直接访问数据库，领域层不依赖云 SDK。
- CI 至少验证构建、适用格式、契约、秘密及依赖问题；后续按已实现能力加入有意义的测试。
- 分支合并流程得到实际验证。远程托管地址和访问权限如未配置，不能把该项标记完成。
- 容器重建不依赖把秘密写进镜像；开发数据明确使用专用卷，真实用户数据不进入仓库。

证据：干净环境构建记录、迁移结果、CI 链接或日志及仓库设置记录。

## 5 阶段 2 邮箱账号与会话

目标：安全确认用户身份，打通真实 Android 至后端的首条业务链。

交付：注册、验证邮箱、登录、登出、会话刷新、必要找回及敏感身份确认流程。

验收标准：

- 邮箱验证前不能获得空间业务访问资格；验证码或验证链接过期、重放及错误用途均被拒绝。
- 正确账号能登录，错误凭据使用一致错误；密码不以明文或可逆密文保存，日志和错误不回显密码及有效凭据。
- 刷新轮换和撤销符合契约；登出、密码重置后不能继续使用应失效的会话。
- 注册、重发、找回和登录存在已配置的防滥用限制；超限结果可预测。
- Android 安全保存凭据，切换账号不显示上一个账号的本地私密状态。
- 受控测试邮箱实际验证投递与找回，不仅依赖邮件服务 mock；生产邮件凭据不进入客户端或 Git。

证据：身份流程验收记录、会话验证结果及脱敏投递记录。不得使用无授权的第三方邮箱做测试。

## 6 阶段 3 双人空间与邀请

目标：验证产品最重要的空间隔离边界。

交付：空间列表及状态、邮箱和用户 ID 邀请、接受拒绝撤销、容量约束。

验收标准：

- A 与 B、A 与 C 可以拥有独立空间；B 与 C 均不能读到对方空间，即使更换资源 ID 或绕过客户端请求。
- 邮箱和用户 ID 两种邀请都可用；只有已注册且验证邮箱的实际接收者可接受。
- 对方确认前没有内容访问资格，知道用户 ID 或邀请 ID 不等于获准加入。
- 邀请过期、撤销、重复接受和并发接受符合确定后的规则；空间始终不超过两位成员。
- 邀请接口和结果查询不成为公开账号目录，不暴露不必要的邮箱或其他空间信息。
- 真实 PostgreSQL 的角色、空间过滤及 RLS 路径经过集成验证，不仅用 mock 证明隔离。

证据：三账号权限矩阵、并发接受结果和数据库角色检查。

## 7 阶段 4 文字梗与共同编辑

目标：交付可以实际记录并回看文字梗的最小可用功能。

交付：梗文字与背景、列表详情、手动保存、编辑模式及版本冲突。

验收标准：

- 双方看到相同的已保存记录，列表分页不跨空间、不重复或漏过稳定数据集中的记录。
- 默认仅原作者可编辑；共同编辑后双方可编辑，且只有原作者能切换模式。
- 两位用户同时保存时，不静默覆盖先完成的更新；客户端提示冲突并保留尚未提交输入。
- 权限刚关闭、目标刚删除或空间已冻结时，旧编辑页面不能继续成功保存。
- 原作者和空间归属不可通过请求字段被修改；直接调用 API 与界面行为遵循同一规则。
- 正文按已选隐私方案加密，数据库、应用日志及崩溃报告中不产生多余明文副本。
- 删除入口只有永久删除链路完整通过后才对真实用户开放，不暂时实现为可恢复删除来冒充已确认规则。

证据：端到端文字记录演示、权限矩阵及并发冲突记录。此阶段的演示使用专用测试数据，不开放真实试用。

## 8 阶段 5 图片与媒体边界

目标：让图片与文字具有相同的权限、生命周期和冻结保护。

交付：选图、上传、处理状态、记录关联、受保护读取、失败重试与未关联资源清理。

验收标准：

- 实际类型、大小、数量及处理资源上限按确定后的配置执行，不只相信文件后缀或客户端声明。
- 图片未准备好或发布失败时不伪装为完整保存成功，客户端能看到可理解的状态。
- 跨空间替换 assetId、猜测资源地址、读取未关联他人资源均失败；正式图片没有永久公共访问链接。
- 原作者或获共同编辑权限的另一方都能按规则添加图片；不能错误要求上传者必须是原作者。
- 已发布图片不能被旧上传请求或客户端覆盖；空间冻结后后台处理不能替换可见内容。
- 孤立资源清理与发布关联并发时不误删；注销及记录删除所需的资源引用可以正确追踪。
- 未来音频处理可以通过明确媒体边界扩展，但本阶段不实现或宣称已支持语音。

证据：私有媒体访问测试、真实对象存储验证、失败与清理竞争场景记录。

## 9 阶段 6 冻结 永久删除与注销

目标：完整验收高风险生命周期规则。基础冻结检查此前已存在，本阶段补齐用户流程与全路径验证。

交付：退出确认与整体冻结、永久删除及任务状态、注销近期验证、预存回执、原作者范围清除和关联空间冻结。

验收标准：

- 任一方退出后整个空间只读，双方重新登录仍能读取相同保留内容；新增、编辑、普通删除和权限切换全部停止。
- 控制并发顺序验证保存、权限切换、图片关联与退出，结果符合已定义的提交边界。
- 活动空间中原作者可删除自己记录，BOTH 模式另一方也可删除；无回收站，错误权限不能触发清除。
- 注销 A 时冻结相关活动空间，撤销 A 会话，并清除 A 最初创建的整个梗及附图，包括已冻结和 B 编辑过的记录。
- B 最初创建的内容及其必要图片和解密能力保留，即使 A 编辑或上传过相关附件。
- 注销提交响应丢失时可用事先保存的秘密回执查询该任务；回执不能读取回忆或恢复登录。
- 清除失败可受控重试，不因重复任务或容器重启误删他人内容；各清除阶段返回真实状态。
- 数据库、媒体和备份删除期限已明确，恢复验证不会使已删除内容重新开放访问。不能仅删除数据库行就将所有清除工作标记完成。

证据：多账号注销对照、冻结并发验证、清除任务恢复和删除后灾备恢复演练记录。

## 10 阶段 7 部署与试用前验收

目标：确认系统能在确定的大陆环境中运行、维护并恢复。

交付：可复现 Docker 镜像、签名试用 APK、部署配置、监控告警、备份恢复与回滚说明、发布清单。

验收标准：

- 试用环境使用 HTTPS，数据库与管理端不直接暴露公网；存储、KMS、邮件和运维权限按用途区分。
- 发布产物绑定确定提交、契约版本、迁移版本、镜像摘要及 APK 校验值，真实配置通过受控渠道注入。
- 容器重建和服务重启不丢失已确认保存的数据；恢复演练覆盖数据库、图片与解密能力。
- 验证从上一可发布版本升级的路径及应用回滚兼容性；数据库不可逆变更不能依赖简单 git revert 或旧镜像解决。
- 监控能发现关键服务、邮件、媒体及清除任务故障；日志和告警不包含私密内容与秘密。
- 按已确定设备、图片、正文与试用规模完成容量验证；在没有约定指标前不声称性能达标。
- 跨空间越权、冻结后写入、错误注销删除、私密资源公开和不可恢复数据损失等阻断问题全部解决。
- 试用人数、数据保留与清除时限、故障联系和暂停方案明确；用户理解共同编辑可删除、退出冻结与注销优先清除的影响。

证据：部署及恢复日志、权限检查、发布清单、设备验证与试用前验收报告。

## 11 阶段 8 小范围试用与修正

目标：验证真实朋友是否能理解并愿意使用，不预先断言产品成功。

交付：限定范围的试用版本、已授权的反馈汇总、缺陷与改进清单、继续或调整结论。

验收标准：

- 试用者能完成配对、记录、回看和权限理解，按已确定观察方案收集结果；不得编造使用率或满意度。
- 不采集梗正文或私密图片用于普通统计，反馈截图与日志有明确授权及脱敏。
- 隐私、删除或数据一致性故障触发暂停相应能力或试用的预案；修复后验证受影响数据。
- 每个发布的修复版本都能追溯至提交和验证证据，不能在服务器上直接改文件形成无法追溯版本。
- 试用结论区分功能可用、规则易懂与持续使用价值，不把没有新错误视为已有市场验证。

观察期限和达标阈值尚未确定，应在试用启动前约定，不在本计划中填写虚假目标。

## 12 全阶段完成定义

一个阶段完成必须同时具备：对应功能、适用的安全与失败场景验证、同步契约及说明、可复现提交与验收证据。不是接口返回过 200、页面能打开或代码已合并就算完成。

允许无依赖的文档、原型和技术验证并行，但阶段验收按依赖推进。权限与删除边界没有验证前，不开放真实用户数据试用。首版未包括的功能不因“架构可扩展”而自动加入任务。

测试按风险选择：权限、并发、注销删除和恢复必须有有意义的自动或集成验证；视觉文案和可逆低影响调整不要求机械增加测试。阶段 0 的静态契约检查不能替代后续服务和数据库验证。

每阶段验收记录建议包含以下字段：

```text
阶段与范围
需求及验收条目
提交 SHA 与执行环境
验证步骤和结果证据
未解决问题及影响
验收结论与记录人
```

## 13 发布版本与回滚

开发分支使用提交 SHA 追踪；阶段通过可记录 `milestone/p1-foundation` 等里程碑标签，它们不是可交付用户的版本。实际试用发布建议从 `v0.1.0-alpha.1` 起编号，修正后新增版本，不移动已发布标签。版本名是建议，不是当前已生成产物。

每次发布记录同一份清单：Git SHA、API 契约版本及摘要、数据库迁移版本、后端及任务镜像摘要、Android versionName/versionCode、APK 校验值和必要运行配置版本。Android versionCode 随发布单调增加；应用发布号与 `/api/v1` 接口主版本不要求一起变化。

镜像由受控构建产生并按摘要部署，避免同一标签指向不同内容。条件允许时保留构建来源与依赖清单；这些信息也不得包含构建秘密。[S3]

回滚优先恢复兼容的应用产物；迁移采用先增加兼容结构、再切换、最后清理的策略，破坏性删除单独评审。恢复旧备份不是普通应用回滚，必须继续执行删除约束，不能把已注销或永久删除的内容重新上线。Git 版本历史不能替代数据库恢复方案。

## 14 下一步执行顺序

先完成阶段 0 的需求与契约收敛，同时准备阶段 1 的仓库和工程模板；随后按账号、空间、文字梗、图片、生命周期、部署验收和试用推进。实际安排开发人员和工期前，还需确定技术栈采用、预算和试用规模。

本轮仅形成计划，没有初始化 Git、创建远程仓库、提交或推送文件，也没有开始部署。若后续执行本计划，相关动作以具体任务授权和实际检查结果推进。
